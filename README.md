# Harvest Now, Decrypt Later · Force Push — music videos

Generative, code-rendered music videos with word-synced karaoke typography, one renderer for several songs
(selected with `?project=` / `--project`, see [Projects](#projects)). Every frame is a deterministic function of song time, so the live preview in the browser and the offline 1080p60 (or 4K60) export are identical.

**Force Push** is a breakup told in Git: a repository called `us`, a commit graph whose `origin/main` gets force-pushed three times, and an ending where the reflog forgets. Treatment: [`docs/FORCE-PUSH-TREATMENT.md`](docs/FORCE-PUSH-TREATMENT.md); cue sheet: [`projects/force-push/cues.md`](projects/force-push/cues.md); inputs, provenance and validation: [`docs/FORCE-PUSH-NOTES.md`](docs/FORCE-PUSH-NOTES.md).

**Harvest Now, Decrypt Later** is sung by the eavesdropper: it intercepts a message in 2021, keeps an encrypted copy, waits patiently while the archive grows, and reads it the year the key falls out. The video tells that as thirteen engraved "plates" (a protocol diagram, a cold-store rack, a patience dial, a dilution refrigerator, a backlog ticket…), cold glacier blue for three minutes and warm only when the key falls out. The concept, style bible and line-by-line cue sheet are in [`docs/TREATMENT.md`](docs/TREATMENT.md); the engine and scene API in [`docs/ENGINE.md`](docs/ENGINE.md).

This repo is a fork of [mexicat/pdoom-video](https://github.com/mexicat/pdoom-video) (MIT): the engine, the timing pipeline and the render tooling come from there; every song-specific part has been replaced. The video was made with Claude (Opus 5.5) in Claude Code.

## Layout

- `projects/<id>/` — one directory per video, everything that belongs to it:
  - `project.json` — title, kind (`song`), and the two inputs: `audio` (the master the analysis reads and the export muxes) and `transcript` (the lyric sheet, with or without `[Section]` headers).
  - `input/` — the master and the lyric sheet as supplied (Harvest: `harvest.wav`, `harvest.txt`; Force Push: `Force Push.wav`, `force-push.txt`, plus the supplied, unused `Force Push.mp3`).
  - `data/` — what the renderer reads, derived by the pipeline and committed: `preview.mp3` (the browser preview), `lines.txt` + `sections.json` (from the sheet), `lyrics.json` (word timings), `audio.json` (beats, bars, sections, envelopes, onsets). Harvest: 96.71 BPM, constant grid; Force Push: ~130.5 BPM, tracked grid. Then the edit: `cues.json` (the cue sheet: timeline entries and one cue per sung line, see `app/src/engine/cues.ts`) and `style.json` (palettes, font roles, the karaoke layer, see `app/src/engine/style.ts`).
  - `cues.md` — the cue sheet resolved to times, generated by `bun scripts/cues.ts`.
  - `tuning.py` (optional) — hand corrections the analysis cannot detect: alignment fixes and anchors, pronunciations, sung-lyric deviations, and any setting pinned instead of detected.
  - `work/` — stems, model outputs, QA plots and the step record (not in the repo; regenerable).
- `vid` — the pipeline (`app/scripts/vid.ts`), see [Pipeline](#pipeline).
- `analysis/` — Python (uv) tools that produce the timing data: Demucs stem separation, CTC forced alignment cross-checked with Whisper (faster-whisper, CUDA), beat/downbeat/onset analysis.
- `app/` — the renderer: TypeScript + three.js, bun + Vite.
  - `src/projects.ts` — the project registry over `projects/*/project.json`; `src/timelines.ts` — a project's timeline: its cue sheet's, or (Harvest) a timeline module.
  - `src/timeline.ts` — Harvest's edit, written before cue sheets: thirteen entries, each cut on the last beat before its first lyric line.
  - `src/force-push/` — Force Push's drawing kit (`kit.ts`: the scene base class, its tokens read from the project's `style.json`) and the commit-graph geometry (`graph.ts`).
  - `src/scenes/` — Harvest's plates (`send`, `ice`, `keep`, `wait`, `qubits`, `passwords`, `newmath`, `ticket`, `petabytes`, `thaw`, `secure`; shared code in `_kit.ts`), Force Push's scenes (`force-push-*.ts`) and the scene library (`lib-*.ts`: 17 scenes any cue sheet can use, each with a parameter schema; registered in `src/library.ts`, shared code in `_lib.ts`; see the gallery: `?gallery` in the preview, `bun scripts/render.ts gallery`).
  - `src/engine/` — renderer core (from upstream; changed here: the palette, per-project data loading, scene render errors recorded so an export fails, the cue sheet and its resolver (`cues.ts`), project styles (`style.ts`), the karaoke layer (`karaoke.ts`)).
  - `scripts/render.ts` — offline renderer (Chrome → raw frames over WebSocket → ffmpeg); `scripts/vid.ts` — the pipeline; `scripts/cues.ts` writes each project's `cues.md`.
  - `test/` — `bun test`: project configuration and selection, the cue sheet's validation, timeline coverage, styles.
- `out/` — renders (not in the repo).

## Requirements

[bun](https://bun.sh), Google Chrome and ffmpeg with libx264. The analysis tools need [uv](https://docs.astral.sh/uv/) and, in practice, an NVIDIA GPU.

On WSL2 the render script uses Chrome through WSLg's X display, which gets hardware GL (ANGLE over D3D12); a headless Chrome there falls back to software. It expects Chrome at `~/opt/chrome/opt/google/chrome/chrome` (override with `CHROME_PATH` or `--chrome`). `bun scripts/render.ts gpu` prints the renderer Chrome ended up with.

|---|---|
| space | play / pause |
| ← / → | seek ±1 s (±5 s with shift) |

## Projects

Each project in `projects/` has its own master, preview, data, cue sheet and style, and default output (`out/<id>.mp4`); nothing falls back to another project's assets, and an unknown or missing project id fails with the list of known ones.

- Preview: http://localhost:5173/?project=force-push (keeps `?t=`, `?only=`, `?scale=`).
- Renderer: `--project force-push` in every mode of `scripts/render.ts`.
- Analysis: `--project force-push` on any `analysis/` script (or `PROJECT=force-push`).

## Render the video

```sh
cd app
bun scripts/render.ts video --project force-push --samples auto --shutter 0.2      # → out/force-push.mp4
bun scripts/render.ts video --project harvest --samples auto --shutter 0.2         # → out/harvest.mp4
```

- **Output:** 1920×1080 at 60 fps, x264 CRF 16, AAC audio from the song's WAV master.
- **Draft:** `--samples 4 --preset veryfast` renders a quick draft.
- **4K:** add `--scale 2` (and `--x264 aq-mode=3:rc-lookahead=30`).
- **Checking a scene:** `bun scripts/render.ts stills --project force-push --t 54.6,58.6 --only chorus1 --out ../out/wip/chorus1`, `sheet --project force-push --cuts --out ../out/force-push-cuts.png` for every scene boundary, `perf --project force-push --from 53 --to 58 --samples 1` for frame times.
- **Checks:** `bun test` (configuration, cue sheet, timeline); `bunx tsc --noEmit -p tsconfig.json && bunx tsc --noEmit -p tsconfig.scripts.json` (types); `bun scripts/render.ts check --project force-push --samples 4` (frames identical in order, in reverse and after seeks); `bun scripts/cues.ts --check` (the cue docs are current).
- A scene that fails to load or throws while rendering fails the run.

Motion blur, adaptive sampling and the render pipeline are described in [`docs/ENGINE.md`](docs/ENGINE.md).

## Pipeline

`./vid` (from the repo root) takes a project from audio + lyric sheet to timing data, and renders it once the project has a cue sheet. Each step runs only when its inputs changed (content hashes in `work/steps.json`; a changed script does not count, use `--force`); committed data without a record is adopted, not recomputed, and steps listed in `project.json`'s `frozen` never run (Harvest: `sung`, `align`).

```sh
./vid new my-song --audio ~/song.wav --transcript ~/lyrics.txt --title "My Song"   # projects/my-song/ (non-WAV audio is decoded to a 48 kHz WAV)
./vid analyze my-song             # sheet -> stems -> vocal features -> CTC emissions -> Whisper -> sung -> align -> beats
./vid status my-song              # which steps are current
./vid analyze my-song --force align,beats
./vid render force-push           # = bun scripts/render.ts video --project force-push --samples auto --shutter 0.2
```

| step | script (`analysis/`) | writes |
|---|---|---|
| sheet | `lyrics_sheet.py` | `data/lines.txt`, `data/sections.json`: `[Section - note]` headers, or stanzas (a repeated stanza is a chorus) |
| stems | `separate.py` | Demucs htdemucs_ft stems (GPU) |
| vocal | `vocal_feats.py` | vocal pitch, loudness and onsets |
| ctc | `ctc_emissions.py` | MMS_FA and wav2vec2-LV60K emissions on the vocal stem's mono, left and right channel (GPU) |
| whisper | `whisper_run.py turbo` | faster-whisper word timestamps; the prompt lists the sheet's uncommon words unless `tuning.py` sets one |
| sung | `sung.py` | `data/sung.json`: lines the vocal sings differently from the sheet. A difference Whisper hears is kept only if the CTC alignment of the line scores at least 8 better with it (no dropped words, near-homophones or unsure hearings) |
| align | `align.py --plots` | `data/lyrics.json`, a QA plot per line and `work/qa/align_report.md` (the words below confidence 0.6) |
| beats | `analyze.py` | `data/audio.json` |

`analyze.py` detects what used to be set by hand per song, and records how in `audio.json`'s `detected`: the tempo window (±7 BPM around the estimate, widened to whole BPM), constant or tracked grid (tracked when a constant grid's local phase error spreads over 40 ms), the bar phase (the snare backbeat, then the strongest chord changes) and the sections (each on the latest downbeat at or before its first sung word). For both songs here the detected tempo window, bar phase and sections reproduce the committed data exactly, as does Force Push's tracked grid (Harvest pins its grid, see below). Numbers in the sheet are aligned as spoken words ("2021" → "twenty twenty one").

What it cannot detect goes into the project's optional `tuning.py`: word starts corrected on the plots (`FIX`, `ANCHORS`), pronunciations (`PRON`), lines the vocal sings differently from the sheet (`SUNG`), and any setting pinned instead of detected (`TEMPO_RANGE`, `GRID`, `BAR_PHASE`, `SECTION_BARS`, `WHISPER_PROMPT`). Stems and work files are stamped with the master's SHA-256, so a changed master never reuses stale caches. The models download a few GB of weights into `analysis/.cache/`.

Inspection tools: `tempo_probe.py` (tempogram peaks and the search window), `sections_bars.py` (the section table), `zoom.py 52.8 58.8 zoom_chorus1` (a zoomed spectrogram/pitch/onset plot with the beat grid), all with `--project <id>`.

Harvest's `data/lyrics.json` predates this pipeline (aligned on an mp3 decode with manual corrections that are not in its `tuning.py`): do not re-align it. Its `tuning.py` also pins the constant grid the published video was cut on, although the song drifts by up to ~150 ms against it.

A new project also needs its edit: `data/cues.json` and, for its look, `data/style.json`. The engine turns the cue sheet into the timeline and checks it when it loads. A malformed cue, a lyric that is not in the transcript or is ambiguous, an anchor word not in its line, a cue outside its section, a sung line with no cue or an entry with no cues all fail, listed together. Scenes that leave the lyrics to the engine get the project-wide karaoke layer: the line being sung, centred low, each word wiped as it is sung, the next line waiting under it, in the palette of the cue on screen. A scene that draws its own lyrics sets `ownsLyrics` (every Force Push scene does), and `"karaoke": false` in `style.json` turns the layer off (Harvest). Generating the edit and the scenes is the plan in [`docs/PIPELINE.md`](docs/PIPELINE.md).
